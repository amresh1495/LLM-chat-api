# LLM Chatbot (Gemma 3 & Llama 3.2)

## Overview

This project provides a Gradio-based chatbot application that allows users to interact with two powerful open-source language models: Google's Gemma 3 (specifically the 12B instruction-tuned version) and Meta's Llama 3.2 (the 3B instruction-tuned version). The application supports dynamic model loading and unloading to help manage computational resources, and features a Retrieval Augmented Generation (RAG) capability to ground responses in user-provided documents.

## Features

*   **Chat with Google Gemma 3 (12B IT)**: Interact with the `google/gemma-3-12b-it` model.
*   **Chat with Meta Llama 3.2 (3B Instruct)**: Interact with the `meta-llama/Llama-3.2-3B-Instruct` model.
*   **Retrieval Augmented Generation (RAG) from local documents**: Augment LLM responses with context retrieved from your own documents.
*   **Model Selection**: Choose the desired LLM from a dropdown menu in the UI.
*   **Dynamic Model Management**: Models are loaded on demand when selected. If one model is loaded and the user chooses to load the other, the first model is automatically unloaded to conserve GPU memory.
*   **Resource Cleanup**: A dedicated button allows users to clear the chat and explicitly unload any active model, freeing GPU resources.
*   **User-Friendly Interface**: Built with Gradio for an intuitive web-based chat experience.

## System Architecture and Flow

This section describes the main components of the application and how they interact.

### Core LLM Integration

At the heart of the application are two advanced large language models (LLMs):

*   **Google's Gemma 3**: Specifically, the `google/gemma-3-12b-it` model, an instruction-tuned variant with 12 billion parameters.
*   **Meta's Llama 3.2**: Specifically, the `meta-llama/Llama-3.2-3B-Instruct` model, an instruction-tuned variant with 3 billion parameters.

These models are powerful tools capable of understanding context, following instructions, and generating human-like text responses.

**Hugging Face `transformers` Library:**
The primary mechanism for accessing and utilizing these open-source models is the Hugging Face `transformers` library. This library is central to the project and provides a vast collection of pre-trained models and tools for Natural Language Processing (NLP). Key functionalities used from this library include:
*   **Model Loading and Inference**: While the library offers detailed tools like `AutoModelForCausalLM` and `AutoTokenizer`, this project leverages the high-level `pipeline` API.
*   **`pipeline` API**: This abstraction simplifies the process of using models for specific tasks. In this application:
    *   Llama 3.2 uses a `"text-generation"` pipeline.
    *   Gemma 3, being a multimodal model, is loaded using an `"image-text-to-text"` pipeline, though it's primarily used for its text generation capabilities in this context. The pipeline handles the underlying model loading, tokenization, and inference calls.

**Client Modules (`GemmaClient`, `LlamaClient`):**
To encapsulate the interaction logic for each LLM, dedicated client classes are implemented in the `llm_integrations/` directory: `GemmaClient` and `LlamaClient`. These modules serve as an abstraction layer, simplifying how the main application (`app.py`) communicates with the LLMs. Their key responsibilities include:

*   **Model Initialization**: Each client is responsible for loading its specific model (e.g., `google/gemma-3-12b-it` for `GemmaClient`) using `transformers.pipeline`. This includes specifying `device_map="auto"` for automatic hardware selection (CPU/GPU) and `torch_dtype=torch.bfloat16` for memory-efficient computation.
*   **Input Formatting**: Before sending a query to the LLM, the clients format the input. This involves constructing a list of messages that typically includes:
    *   A system prompt (e.g., "You are a helpful AI assistant.").
    *   The existing chat history, converted into the model's expected format.
    *   The current user query, potentially prepended with context retrieved by the RAG system.
*   **Model-Specific Structures**: The clients handle any nuances in prompt structure required by each model. For example, Gemma 3's pipeline (when used for chat-like interactions with text) expects message content to be a list of dictionaries (e.g., `[{"type": "text", "text": "..."}]`), which the `GemmaClient` ensures.
*   **Response Generation**: They invoke the loaded pipeline with the formatted messages and generation parameters (e.g., `max_new_tokens`, `temperature`, `do_sample`).
*   **Output Extraction**: The raw output from the pipeline can be complex. The clients parse this output to extract the actual text response generated by the assistant.

These client modules ensure that the main application logic remains clean and independent of the specific requirements of each LLM.

### RAG Pipeline Components

**Conceptual Overview of RAG:**
Retrieval Augmented Generation (RAG) is a technique used to enhance the responses of Large Language Models (LLMs). Instead of relying solely on its pre-trained knowledge, an LLM with RAG capabilities can access and incorporate information from external data sources.

In this application, RAG allows the chatbot to ground its responses in information retrieved from a user-provided local document collection. This helps in providing answers that can be more accurate, up-to-date if the documents are current, or specific to the domain covered by the documents, rather than generic pre-trained knowledge.

The RAG pipeline implemented here involves several key components:

1.  **Document Loader (`RAGProcessor`)**:
    *   **Source**: User-provided text files (extensions `.txt` and `.md`) located in the `./data/` directory.
    *   **Function**: The `RAGProcessor` reads the content of these files. This is the first step in making external knowledge available to the system.

2.  **Text Splitter/Chunker (`RAGProcessor`)**:
    *   **Strategy**: After loading, documents are split into smaller, manageable text segments called "chunks." The current implementation in `RAGProcessor` uses a simple paragraph-based chunking strategy, splitting the text based on double newline characters (`\n\n`).
    *   **Rationale**: Chunking is crucial because:
        *   LLMs have maximum input context lengths; processing entire documents at once is often infeasible.
        *   Embedding models, which convert text to numerical representations, generally perform better and capture semantics more effectively on coherent, reasonably sized text segments.
        *   Smaller chunks allow for more targeted and precise retrieval of information relevant to a specific user query.

3.  **Embedding Model (`sentence-transformers`)**:
    *   **Model Used**: The system utilizes the `all-MiniLM-L6-v2` model by default (this can be configured in `RAGProcessor`). This is a lightweight but highly effective model from the `sentence-transformers` library, designed to generate dense vector representations (embeddings) for sentences or paragraphs.
    *   **Purpose**: Each text chunk is converted into an embedding. This embedding is a numerical vector that captures the semantic meaning of the chunk. Text segments with similar meanings will have embeddings that are close together in vector space.

4.  **Vector Store (FAISS)**:
    *   **Library**: `faiss-cpu` (Facebook AI Similarity Search) is used for efficient similarity searching in high-dimensional vector spaces. The `-cpu` version is used for broader compatibility without requiring a dedicated GPU for the index.
    *   **Index Type**: `IndexFlatL2`. This index type stores the raw, uncompressed embeddings and, during a search, performs an exhaustive comparison of the query vector against all stored chunk embeddings using L2 distance (Euclidean distance). While simple and exact, it's well-suited for datasets of moderate size where search speed is acceptable.
    *   **Function**: The FAISS index stores all the embeddings generated from the document chunks. When a user query is received, it's also embedded, and this query embedding is used to search the FAISS index for the document chunks with the most similar embeddings.
    *   **Storage**: The constructed FAISS index is saved to disk (by default, to `./data/faiss_index.idx`). To reconstruct the actual text from a search result (which returns indices of vectors), the text chunks themselves are also saved separately in a JSON file (e.g., `./data/faiss_index_chunks.json`).

5.  **Retriever (`RAGProcessor`)**:
    *   **Process**:
        1.  The user's incoming query is first converted into an embedding using the same `sentence-transformers` model (`all-MiniLM-L6-v2`).
        2.  This query embedding is then used to search the FAISS index. The search operation returns the indices of the `top_k` document chunks whose embeddings are closest (most similar) to the query embedding.
    *   **Output**: The actual text content of these `top_k` most similar chunks is retrieved from the stored list of chunks. This collection of text forms the "retrieved context."

6.  **Prompt Augmentation (Performed in `LLM Clients`)**:
    *   **How it works**: The retrieved context (which is a string formed by concatenating the relevant text chunks, typically separated by newlines or other markers) is then prepended to the user's original query. This augmented prompt is what gets sent to the selected LLM (Gemma or Llama).
    *   **Example Prompt Structure**: The LLM receives a prompt structured roughly as follows:
        ```
        Based on the following context:
        [Retrieved chunk 1 text]

        ---

        [Retrieved chunk 2 text]
        ...

        User query: [Original user query]
        ```
    *   **Goal**: By providing this relevant, extracted information directly within the prompt, the LLM is equipped with specific knowledge to draw upon when formulating its response. This helps to make the answer more factual, detailed, and grounded in the provided documents.

### RAG - Data Ingestion and Indexing Flow

This section outlines how documents are processed and how the searchable RAG index is built and maintained. This process allows the system to retrieve relevant information from your local files.

1.  **User Action: Placing Documents**:
    *   The user begins by placing their custom document files (plain text `.txt` or Markdown `.md`) into the `./data/` directory at the root of the project. These documents contain the knowledge base the RAG system will use.

2.  **User Action: Initializing RAG Processor**:
    *   In the Gradio UI, under the "LLM and RAG Controls" tab, the user clicks the "Initialize RAG Processor" button.
    *   This action triggers the creation of an instance of the `RAGProcessor` class (from `llm_integrations/rag_processor.py`).
    *   Upon initialization, the `RAGProcessor` immediately attempts to load any pre-existing FAISS index (e.g., `faiss_index.idx`) and its corresponding document chunks (e.g., `faiss_index_chunks.json`) from the `./data/` directory. This allows the RAG index to persist across application restarts if it has been built previously. The embedding model (`all-MiniLM-L6-v2` by default) is also loaded at this stage.

3.  **User Action: Building/Updating the Index**:
    *   To incorporate new documents, or changes to existing ones, the user clicks the "Build/Update RAG Index from 'data/' dir" button in the UI. This step is essential to make new information searchable.

4.  **Internal Process: Document Loading and Chunking (`RAGProcessor._load_and_chunk_documents`)**:
    *   Triggered by the "Build/Update RAG Index" action, the `RAGProcessor` scans the `./data/` directory for all files with `.txt` or `.md` extensions.
    *   The content from each valid document file is read into memory.
    *   This raw text is then segmented into smaller, more manageable "chunks." The current strategy splits text based on double newline characters (`\n\n`), effectively treating paragraphs as individual chunks.

5.  **Internal Process: Embedding Generation (`RAGProcessor.build_index` using Sentence Transformer)**:
    *   Each text chunk obtained from the previous step is processed by the pre-loaded Sentence Transformer model (e.g., `all-MiniLM-L6-v2`).
    *   This model converts each chunk into a dense numerical vector, known as an embedding. This vector captures the semantic meaning of the text chunk.

6.  **Internal Process: FAISS Index Construction (`RAGProcessor.build_index` using FAISS)**:
    *   A new FAISS index is created. The application uses `IndexFlatL2`, which is suitable for exact similarity search using L2 (Euclidean) distance between vectors.
    *   The embeddings generated for all document chunks are then added to this FAISS index.

7.  **Internal Process: Saving Index and Chunks (`RAGProcessor.build_index`)**:
    *   The newly constructed FAISS index, containing all the chunk embeddings, is saved to disk as a file (e.g., `./data/faiss_index.idx`).
    *   Crucially, the original text chunks themselves are also saved, typically as a JSON file (e.g., `./data/faiss_index_chunks.json`). This file maintains a mapping (usually by order or ID) that allows the system to retrieve the actual text of a chunk when its embedding is identified as relevant by FAISS (since FAISS only stores the numerical vectors).

8.  **Feedback to User**:
    *   Throughout the initialization and index-building process, status messages are displayed in the "RAG Status" textbox in the Gradio UI. These messages inform the user about the success of operations, the number of chunks loaded/indexed, whether an existing index was found, or if any errors occurred. This feedback loop helps the user understand the state of the RAG system and whether it's ready for use.

This flow ensures that user-provided documents are efficiently processed, indexed, and made available for retrieval to augment the LLM's responses.

### RAG - Query and Augmented Generation Flow

This section details the sequence of operations when a user submits a query and RAG is enabled, leading to an LLM response augmented by retrieved document context.

1.  **User Action: Input Query and Enable RAG**:
    *   The user types their query into the chat input field in the Gradio UI's "Chat Interface" tab.
    *   On the "LLM and RAG Controls" tab, the user ensures that the "Enable RAG for Chatbot Responses" checkbox is checked.
    *   The user submits their query (e.g., by clicking the "Send" button or pressing Enter).

2.  **Application Logic (`app.py` - `chat_function`)**:
    *   The `chat_function` in `app.py` is invoked, receiving the user's query, the current chat history, the name of the selected LLM, and the boolean status of the "Enable RAG" checkbox.
    *   The function first checks if RAG is enabled.
    *   If RAG is enabled, it then verifies if the `rag_processor` (the global instance of `RAGProcessor`) is initialized and if its FAISS index (`rag_processor.index`) and document chunks (`rag_processor.document_chunks`) are loaded and available.

3.  **Context Retrieval (`RAGProcessor.retrieve_context()`)**:
    *   If the conditions in step 2 are met (RAG enabled and index ready), the user's raw query string is passed to the `rag_processor.retrieve_context()` method.
    *   **Query Embedding**: Inside `retrieve_context()`, the query string is transformed into a numerical vector (embedding) using the same Sentence Transformer model (e.g., `all-MiniLM-L6-v2`) that was used during the indexing phase. This ensures that the query and the document chunks are represented in the same semantic space.
    *   **Similarity Search**: The generated query embedding is then used to search the FAISS index. FAISS efficiently compares this query embedding against all the document chunk embeddings stored within the index. It identifies the `top_k` chunks (the default is 3, but this can be adjusted) whose embeddings are most semantically similar (closest in vector space) to the query embedding.
    *   **Chunk Retrieval**: The search returns the indices of these `top_k` most relevant chunks. The `RAGProcessor` then uses these indices to look up the actual text of these chunks from its stored `document_chunks` list.
    *   **Context Assembly**: The textual content of the retrieved chunks is combined into a single string. This string, typically with chunks separated by double newlines or other markers, becomes the `retrieved_context`.

4.  **Handling No RAG / Index Not Ready**:
    *   If the "Enable RAG" checkbox is unchecked, or if it is checked but the `rag_processor` is not initialized or its index is not ready (e.g., not built or failed to load), the `retrieved_context` variable remains `None` or empty.
    *   In such cases, the application proceeds to generate a response using only the LLM's pre-trained knowledge, without any external context augmentation.

5.  **Prompt Construction for LLM (within `GemmaClient` or `LlamaClient`)**:
    *   The original user query, the (potentially empty) `retrieved_context`, and the conversation history are passed to the `generate_response` method of the currently selected LLM's client (`GemmaClient` or `LlamaClient`).
    *   Inside the client module, a final prompt is constructed for the LLM. If `retrieved_context` is available and contains text, it is prepended to the user's original query. A typical structure for this augmented user message is:
        ```
        Based on the following context:
        [Retrieved chunk 1 text]

        ---

        [Retrieved chunk 2 text]
        ...

        User query: [Original user query]
        ```
    *   This augmented user message, along with the system prompt and the conversation history, is formatted into the specific message structure expected by the target LLM (Gemma or Llama).

6.  **LLM Inference**:
    *   The fully constructed prompt (which now includes the retrieved context if RAG was successful) is sent to the chosen LLM (Gemma 3 or Llama 3.2) through the Hugging Face `transformers.pipeline` instance held by the client.
    *   The LLM processes this input and generates a response. Because the prompt includes relevant context, the LLM can produce an answer that is more informed by, and grounded in, the user-provided documents.

7.  **Display Response**:
    *   The text response generated by the LLM is extracted from the pipeline's output by the client module.
    *   This final response is then returned to `app.py`, which updates the Gradio chat interface, displaying the chatbot's answer to the user.

This flow allows the chatbot to dynamically leverage external knowledge from local documents, providing more relevant and contextually aware responses when the RAG feature is utilized.

### Conceptual Details and Considerations for RAG

This section discusses some of the broader benefits, limitations, and important considerations when working with the RAG (Retrieval Augmented Generation) approach implemented in this application.

**Benefits of RAG**:

*   **Improved Factual Grounding**: RAG helps to ground the LLM's responses in specific, verifiable information sourced directly from the provided document corpus. This reduces reliance on the LLM's parametric (internal) knowledge, which can sometimes be opaque or outdated.
*   **Access to Up-to-Date Information**: Standard LLMs are trained on static datasets, meaning their knowledge cutoff is fixed at the time of training. RAG allows the LLM to access and utilize information that may be more current than its last training update, provided the document corpus is kept up-to-date by the user.
*   **Domain-Specific Knowledge**: The system can effectively answer questions or generate text related to niche or proprietary domains if relevant documents are provided. This allows the LLM to perform tasks that would be impossible with only its general training data.
*   **Reduced Hallucinations**: By providing relevant context directly in the prompt, RAG can significantly reduce the likelihood of the LLM inventing facts, details, or sources (a phenomenon known as "hallucination"). The LLM has a textual basis for its answers.
*   **Transparency (Implicit)**: Although the current UI does not explicitly cite the source documents for each part of an answer, the very nature of RAG means responses are derived from the provided corpus. In more advanced implementations, this can be extended to include direct citations, enhancing trust and verifiability.

**Limitations and Important Considerations**:

*   **Quality of Retrieval ("Garbage In, Garbage Out")**:
    *   The overall effectiveness of the RAG system is critically dependent on the quality, relevance, and organization of the documents within the knowledge base (`./data/` directory).
    *   If the retrieved context is irrelevant to the query, poorly written, or contains contradictory information, it can negatively impact the LLM's output. This might lead to more confusion, reinforce incorrect information, or result in nonsensical answers.
*   **Embedding Model Choice and Alignment**:
    *   The chosen embedding model (default: `all-MiniLM-L6-v2`) plays a vital role. Its suitability for the type of content in your documents and the nature of expected user queries is crucial for optimal retrieval performance.
    *   A mismatch (e.g., using a highly technical embedding model for colloquial documents, or vice-versa) can lead to suboptimal retrieval, where the system fails to find the most relevant chunks.
*   **Chunking Strategy**:
    *   The method used for splitting documents into chunks (currently paragraph-based via `\n\n`) is a key hyperparameter.
    *   **Too Small**: Chunks that are too small might lack sufficient context for the LLM to understand the retrieved information or for the embedding model to generate a meaningful representation.
    *   **Too Large**: Chunks that are too large might introduce excessive noise (irrelevant information within the chunk), dilute the specific relevant text, or even exceed the LLM's context window limits when combined with the query and chat history.
*   **LLM Context Window**:
    *   All LLMs have a finite context window – the maximum amount of text (tokens) they can consider at any one time.
    *   The augmented prompt, which includes the system message, chat history, the (potentially long) retrieved context, and the user's original query, must fit within this window. If the combined input is too long, it may lead to truncation (loss of information) or processing errors.
*   **Index Updates and Maintenance**:
    *   The FAISS index, once built, is static. If documents in the `./data/` directory are added, removed, or significantly modified, the index does **not** automatically update.
    *   The user must manually click the "Build/Update RAG Index" button in the UI to re-process the documents and reflect these changes in the searchable index.
*   **Scalability for Large Datasets**:
    *   The current implementation uses `faiss-cpu` with `IndexFlatL2`. This setup is generally suitable for small to moderate-sized document collections where exhaustive L2 distance search is feasible.
    *   For very large datasets (e.g., millions of documents or more), this approach might become slow in terms of search speed and could be memory-intensive. Production-scale RAG systems often employ more advanced FAISS indexing strategies (e.g., those involving quantization like `IndexIVFPQ`) or dedicated vector database solutions (e.g., Pinecone, Weaviate, ChromaDB, Milvus) for better scalability and performance.
*   **Handling Noisy or Contradictory Retrievals**:
    *   The retrieval process is based on semantic similarity, but there's no guarantee that the retrieved context will always be perfectly relevant, entirely free of noise, or devoid of contradictions (especially if the source documents themselves contain such issues).
    *   The LLM must be robust enough to handle such situations, or the prompt engineering must guide it to critically evaluate or synthesize the provided context. This can be a challenging aspect of advanced RAG tuning.
*   **Cost of Embedding and Indexing**:
    *   While `sentence-transformers` and `faiss-cpu` are generally efficient, the initial process of generating embeddings for all chunks and building the FAISS index can be computationally intensive and time-consuming, especially for very large document sets. Subsequent updates might also require re-processing.

Understanding these benefits and limitations is key to effectively utilizing and troubleshooting the RAG functionality in this application.


## How to Use

The application interface is organized into two main tabs: "LLM and RAG Controls" and "Chat Interface".

**1. LLM and RAG Controls Tab:**

*   **LLM Selection and Loading**:
    1.  **Select an LLM Model**: Choose either "Gemma 3 (12B IT)" or "Llama 3.2 (3B Instruct)" from the dropdown.
    2.  **Load Selected LLM**: Click this button to load the chosen model. Status messages will appear in the "LLM Status" box. This might take time, especially on the first load if model weights need downloading.
*   **RAG (Retrieval Augmented Generation) Controls**:
    1.  **Prepare Documents**: Place your custom `.txt` or `.md` document files into the `data/` directory located in the project's root folder.
    2.  **Initialize RAG Processor**: Click this button. It prepares the RAG system by loading the embedding model and any existing pre-built FAISS index from the `data/` directory. Check the "RAG Status" box for confirmation.
    3.  **Build/Update RAG Index**: After adding new documents or modifying existing ones in the `data/` directory, click this button. This will process all documents in `data/`, create embeddings, and build/update the FAISS index. This step is crucial for new documents to be searchable.
    4.  **Enable RAG for Chatbot Responses**: Check this checkbox if you want the chatbot to use the RAG system. When enabled, the chatbot will first search your documents for relevant context before generating a response. If unchecked, it will rely solely on its pre-trained knowledge.

**2. Chat Interface Tab:**

1.  **Ensure Model is Loaded**: Before chatting, make sure an LLM is loaded (see LLM controls).
2.  **Enable RAG (Optional)**: If you want to use RAG, ensure it's initialized, an index is built, and the "Enable RAG" checkbox is checked on the "LLM and RAG Controls" tab.
3.  **Chat**: Type your message into the message textbox and either click "Send" or press Enter. The model's response will appear in the chat window. If RAG is enabled, the response may be informed by your documents.
4.  **Switch Models**: To switch LLMs, go back to the "LLM and RAG Controls" tab, select the new model, and click "Load Selected LLM". The previously active LLM will be unloaded automatically.
5.  **Clear and Unload**: To clear the chat history and unload any active LLM (freeing GPU memory), click the "Clear Chat & Unload Models" button available on the "Chat Interface" tab. The RAG index and processor will remain loaded as they are less resource-intensive.
